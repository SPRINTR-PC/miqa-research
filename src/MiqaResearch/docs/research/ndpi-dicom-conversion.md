# *.ndpi to DICOM Conversion Tooling Comparison

**Issue:** #107 (part of map issue #98)
**Date:** 2026-09-17
**Scope:** Compare tooling for converting Hamamatsu `*.ndpi` whole-slide pathology images into standards-conformant DICOM: `wsidicom`/`wsidicomizer`, `openslide-python` + a custom `pydicom`/`highdicom` writer, and Hamamatsu's own NDP.view2/NDP SDK path. Evaluated against this repo's existing WADO-RS frame-retrieval code path (`MiqaResearch/interfaces/http/api/views/dicom/wado.py`), which anticipates serving tiled, pathology-style J2K/JPEG-encoded DICOM frames. This repo's `pyproject.toml` currently depends on `pydicom` only — none of `openslide`, `tifffile`, `wsidicom`, `wsidicomizer`, or `highdicom` are installed today.

## Method / primary sources used

- GitHub repositories and their license metadata (GitHub license-detection API plus the actual `LICENSE`/`LICENCE` file text) for `imi-bigpicture/wsidicom`, `imi-bigpicture/wsidicomizer`, `imi-bigpicture/opentile`, `openslide/openslide-python`, `ImagingDataCommons/highdicom`, and `pydicom/pydicom`.
- Source code inspection: `wsidicom/uid.py` and `wsidicom/instance/dataset.py` (SOP Class / transfer syntax handling), `openslide/src/openslide-vendor-hamamatsu.c` (NDPI vendor driver existence), a full recursive tree listing and code search of the `highdicom` repo for any Whole Slide Microscopy IOD support.
- PyPI project pages and PyPI JSON metadata for `wsidicom` (https://pypi.org/project/wsidicom/) and `wsidicomizer` (https://pypi.org/pypi/wsidicomizer/json) — license classifiers, dependency pins, package descriptions.
- README files fetched from source (`wsidicom`, `wsidicomizer`, `opentile`) for stated format support and IOD targeting.
- `openslide.org/formats/hamamatsu/` — OpenSlide's own documentation of its NDPI ("hamamatsu" vendor) backend and its known limitations.
- DICOM standard text: PS3.4 Annex B.5 (SOP Class registry, https://dicom.nema.org/medical/dicom/current/output/chtml/part04/sect_B.5.html) confirming SOP Class UID 1.2.840.10008.5.1.4.1.1.77.1.6, and PS3.6 Annex A (Transfer Syntax registry, https://dicom.nema.org/medical/dicom/current/output/chtml/part06/chapter_A.html) confirming transfer syntax UIDs 1.2.840.10008.1.2.4.90/.91. DICOM Supplement 145 (https://www.dicomstandard.org/News/ftsup/docs/sups/sup145.pdf) as origin context for the VL Whole Slide Microscopy Image IOD.
- Hamamatsu's own product pages for NDP.view2 (https://www.hamamatsu.com/eu/en/product/life-science-and-medical-systems/digital-slide-scanner/U12388-01.html) and NDP.serve3 (https://www.hamamatsu.com/jp/en/product/life-science-and-medical-systems/digital-slide-scanner/U13173-03.html), plus Hamamatsu's public camera SDK license pages (DCAM-SDK4/DCIMG-SDK) as a licensing-model contrast/reference point.

## wsidicom + wsidicomizer

**Licensing.** Both `imi-bigpicture/wsidicom` and `imi-bigpicture/wsidicomizer` are Apache License 2.0, confirmed via the GitHub license-detection API (`repos/imi-bigpicture/wsidicom/license` and `repos/imi-bigpicture/wsidicomizer/license`, both reporting `spdx_id: "Apache-2.0"`) and via the actual `LICENCE` files in each repo (note British spelling: `LICENCE`, not `LICENSE`) — full Apache-2.0 text, copyright Sectra AB. The source header in `wsidicom/uid.py` reads "Copyright 2021 SECTRA AB ... Licensed under the Apache License, Version 2.0." wsidicomizer's dependency `opentile` (also Sectra AB) is likewise Apache-2.0, confirmed the same way. PyPI classifiers for both `wsidicom` (https://pypi.org/project/wsidicom/) and `wsidicomizer` (https://pypi.org/pypi/wsidicomizer/json) confirm Apache-2.0. This is fully permissive for a commercial/research product — no copyleft obligations.

**`.ndpi` support.** `wsidicom` itself has none — it only reads/writes datasets that are already DICOM WSI (from file, DICOMDIR, or DICOMweb). `wsidicomizer`'s README (https://github.com/imi-bigpicture/wsidicomizer/blob/main/README.md) explicitly names **"Hamamatsu ndpi"** as a supported source format under its **lossless conversion** tier, alongside Aperio SVS and Philips TIFF — these are handled via the `opentile` library rather than `openslide-python`. `opentile`'s own README (https://github.com/imi-bigpicture/opentile/blob/main/README.md) states it supports "Hamamatsu Ndpi" among other tiled-TIFF WSI formats and is built to "allow compressed tiles to be losslessly read from WSI TIFFs" — i.e. it repackages NDPI's existing JPEG-compressed tile bytes directly into DICOM frames without decoding and re-encoding. (A second, *lossy*-conversion tier requires the optional `openslide` extra and covers other vendors' proprietary formats — Mirax MRXS, Leica SCN, Sakura SVSLIDE, Trestle TIF, Ventana BIF/TIF, and Hamamatsu's older VMS/VMU container — but NDPI specifically does not need that path.)

**Output conformance.** `wsidicom/instance/dataset.py` (https://github.com/imi-bigpicture/wsidicom/blob/main/wsidicom/instance/dataset.py) imports `VLWholeSlideMicroscopyImageStorage` from `pydicom.uid` and gates dataset acceptance on the SOP Class UID matching it — i.e. it hard-checks for 1.2.840.10008.5.1.4.1.1.77.1.6, the exact IOD this repo's WADO-RS path anticipates. `wsidicom/uid.py` (https://github.com/imi-bigpicture/wsidicom/blob/main/wsidicom/uid.py) imports pydicom's standard `AllTransferSyntaxes`/`UID_dictionary` (covering JPEG Baseline 1.2.840.10008.1.2.4.50, JPEG2000 Lossless .90, and JPEG2000 .91) and additionally self-registers JPEG XL transfer syntaxes not yet in pydicom's own dictionary, showing active maintenance of transfer-syntax coverage. `wsidicomizer`'s CLI exposes an explicit output-encoding choice — `jpeg | jpeg2000 | htjpeg2000 | jpegxl` — and, per its README, uses opentile's lossless tile pass-through for formats opentile supports (which includes NDPI). Since `WsiDicomizer` writes output through wsidicom's `save()`, produced datasets inherit wsidicom's SOP-Class/transfer-syntax handling; the exact default transfer syntax wsidicomizer emits for NDPI specifically (native JPEG-baseline pass-through vs. forced re-encode) was not independently confirmed inside wsidicomizer's own source in this pass — flagged as an open item below.

**Integration pattern.** Genuinely one-shot: `wsidicomizer -i <path_to_ndpi> -o <output_folder>` from the CLI, or the `WsiDicomizer` Python class, produces a ready DICOM file set directly from an `.ndpi` file — no bespoke tiling or pixel-encoding glue required. PyPI metadata (https://pypi.org/pypi/wsidicomizer/json) pins `pydicom>=3.0.0` and `wsidicom>=0.35.0,<0.36.0` as core dependencies, plus `opentile` (0.25.x range) and `tiffslide`; `openslide-python>=1.4.6,<2.0.0` is only an optional extra (for the lossy-tier formats, not needed for NDPI).

## openslide-python + pydicom/highdicom (DIY)

**Licensing.** `openslide/openslide-python`'s GitHub license API reports `spdx_id: "LGPL-2.1"` (GNU Lesser General Public License v2.1). This is more restrictive than Apache-2.0/MIT: permissive enough to depend on as an unmodified, dynamically-linked package, but LGPL's copyleft terms attach if the library is modified or statically linked, which would need a compliance review if this repo ever vendors rather than depends on it. `ImagingDataCommons/highdicom`'s GitHub license API reports `spdx_id: "mit"`. `pydicom`'s `LICENSE` file (fetched raw from `pydicom/pydicom`) confirms MIT, with a note that some auto-generated private-dictionary data (GDCM-derived) is BSD-3 — already a repo dependency today, so no new licensing cost.

**`.ndpi` support.** OpenSlide reads NDPI natively through a dedicated Hamamatsu vendor backend (source: `openslide/src/openslide-vendor-hamamatsu.c`; documented at https://openslide.org/formats/hamamatsu/, CC BY-SA 4.0). That page documents real correctness caveats a hand-rolled converter would inherit: "Multiple focal planes are ignored, only focal plane 0 is read" (loses z-stack data if present); NDPI is TIFF-like but libtiff cannot read its headers directly due to a `RowsPerStrip` tag overflow bug in how Hamamatsu wrote the file, requiring a workaround; JPEG data can exceed the JPEG 65535-pixel dimension limit and, on pyramid levels lacking restart markers, declared TIFF `ImageWidth`/`ImageHeight` may not match actual JPEG dimensions; and NDPI files can exceed the classic-TIFF 4GB limit despite being TIFF-based. wsidicomizer deliberately routes NDPI through `opentile` instead of openslide specifically to get lossless, spec-faithful tile pass-through and sidestep these issues.

**Output conformance.** Neither `openslide-python` nor `highdicom` nor `pydicom` provides a ready-made DICOM WSI writer. highdicom's own README (https://github.com/ImagingDataCommons/highdicom/blob/master/README.md) enumerates exactly what it can create: Annotations, Parametric Map images, Segmentation images, Structured Report documents, Secondary Capture images, Key Object Selection documents, Legacy Converted Enhanced CT/PET/MR images, and Softcopy Presentation State instances. **The VL Whole Slide Microscopy Image IOD is absent from that list.** A recursive repo-tree listing and a code search for the literal string `VLWholeSlideMicroscopyImage` inside `ImagingDataCommons/highdicom` returned no results — no file, module, or reference to the WSI SOP class exists in that codebase. (This is an absence-of-evidence finding based on GitHub's indexed search and the current README; it would not surface undocumented support in an unindexed branch, though none was found.) highdicom does have pathology-adjacent *reading*/pixel-transform helpers, but no WSI-IOD *writer* class.

**Integration pattern.** Building a conformant output would require hand-assembling the Whole Slide Microscopy Image Module, the Multi-frame Functional Groups Module, tiling/pyramid geometry, and frame-level J2K/JPEG pixel data encoding directly against the PS3.3 IOD text, using bare `pydicom` (optionally borrowing highdicom's lower-level generic helpers where they happen to apply). This is the highest-effort, highest-conformance-risk of the three software candidates — every module and encoding choice that `wsidicom` already implements and tests would need to be reproduced and validated from scratch.

## Hamamatsu vendor SDK (NDP.view2 / NDP.serve3)

Hamamatsu's own product page for NDP.view2 (U12388-01, https://www.hamamatsu.com/eu/en/product/life-science-and-medical-systems/digital-slide-scanner/U12388-01.html) states it "is free to use with Hamamatsu format slides," runs on Windows 10/11 and current macOS versions, and is explicitly labeled "only for research use and is not for In Vitro Diagnostic (IVD)." The page makes no mention of DICOM export or of any developer SDK. A related product, NDP.view2 Plus, adds viewing support for other vendors' WSI formats (SVS, SCN, MRXS, CZI, VSI per its datasheet, found via search but not independently re-fetched in full in this pass) — again a viewer feature, not a converter or SDK. NDP.serve3 (https://www.hamamatsu.com/jp/en/product/life-science-and-medical-systems/digital-slide-scanner/U13173-03.html) is a network slide-sharing web server for distributing WSI over an intranet/internet, per its own product description — also not a DICOM export tool.

No public NDPI file-format specification could be located, which is consistent with OpenSlide's Hamamatsu backend being a reverse-engineered driver (workarounds for undocumented TIFF-tag misuse, etc., as detailed above) rather than one built against a published spec. For contrast: Hamamatsu *does* publish a public, self-service developer-SDK licensing model for its camera product lines (DCAM-SDK4, https://www.hamamatsu.com/us/en/product/cameras/software/driver-software/dcam-sdk4.html; DCIMG-SDK, https://www.hamamatsu.com/us/en/product/cameras/driver-software/dcimg-sdk.html) — a free, nonexclusive, nontransferable, revocable, limited-use license — but no equivalent public "NDP SDK" page, NDPI reader/writer library, or DICOM-export licensing terms could be found on Hamamatsu's site in this research pass. If such capability exists at all, it is not self-service and would require direct outreach to Hamamatsu, likely under NDA or an existing business relationship.

## SOP Class UID and transfer syntax specifics

- **SOP Class UID `1.2.840.10008.5.1.4.1.1.77.1.6`** ("VL Whole Slide Microscopy Image Storage") is confirmed directly in the DICOM standard's SOP Class registry, PS3.4 Annex B.5 (https://dicom.nema.org/medical/dicom/current/output/chtml/part04/sect_B.5.html). This IOD originates from DICOM Supplement 145 (ratified 2010, https://www.dicomstandard.org/News/ftsup/docs/sups/sup145.pdf), which defined the Visible Light Whole Slide Microscopy Image IOD for digital pathology.
- **Transfer syntax UIDs**, confirmed from PS3.6 Annex A (https://dicom.nema.org/medical/dicom/current/output/chtml/part06/chapter_A.html): `1.2.840.10008.1.2.4.90` = "JPEG 2000 Image Compression (Lossless Only)" (`JPEG2000Lossless`); `1.2.840.10008.1.2.4.91` = "JPEG 2000 Image Compression" (`JPEG2000`).
- **Which candidates explicitly target these**: only `wsidicom` (and, by extension, `wsidicomizer`, which writes through it) was directly confirmed in source code to check/target `VLWholeSlideMicroscopyImageStorage` and to carry JPEG-Baseline/JPEG2000 transfer syntax support via pydicom's standard UID dictionary. Neither `highdicom` nor `openslide-python` has any code path or module targeting this SOP Class — a DIY build on top of them would need to construct IOD conformance (Whole Slide Microscopy Image Module, Multi-frame Functional Groups, Specimen module, etc.) from the PS3.3 standard text directly against bare `pydicom`.

## Verdict / recommendation

Pursue **`wsidicomizer` + `wsidicom`** as the primary path for `.ndpi` → DICOM conversion in this repo. It is the only candidate of the three that simultaneously (a) explicitly, by name, supports Hamamatsu NDPI as a first-class, lossless-conversion source format via `opentile`; (b) is purpose-built to emit the VL Whole Slide Microscopy Image IOD / SOP Class UID 1.2.840.10008.5.1.4.1.1.77.1.6 that this repo's WADO-RS path (`MiqaResearch/interfaces/http/api/views/dicom/wado.py`) already anticipates serving; (c) supports the frame encodings (JPEG Baseline and JPEG2000, transfer syntaxes .90/.91) that path expects; and (d) is a one-shot CLI/library call rather than bespoke glue, minimizing conformance risk versus hand-rolling a writer on `pydicom`/`highdicom`. Licensing is fully permissive (Apache-2.0 across `wsidicom`, `wsidicomizer`, and their `opentile` dependency) and requires no copyleft compliance handling, unlike the `openslide-python`-based DIY path (LGPL-2.1).

The `openslide-python` + `pydicom`/`highdicom` DIY path should be kept only as a fallback for source formats `wsidicomizer`/`opentile` cannot handle losslessly (e.g. older Hamamatsu VMS/VMU, or other vendors' proprietary formats not in `opentile`'s list) — not for NDPI itself, where a purpose-built lossless path already exists and where `highdicom` provides no WSI-IOD writer to lean on. The Hamamatsu vendor SDK path is not currently actionable from public information: no DICOM export capability or public NDPI SDK/license terms were found, so this branch should be considered closed pending any information that only a direct Hamamatsu relationship could surface.

**Open items / needs a follow-up spike:**

2. Empirically verify WADO-RS compatibility: feed a `wsidicomizer`-produced DICOM file set through the repo's existing `wado.py` frame-retrieval path and confirm the transfer syntax(es) it actually emits.
3. Confirm which exact transfer syntax `wsidicomizer` emits by default for NDPI (native JPEG-baseline pass-through vs. forced JPEG2000 re-encode) and decide whether the WADO-RS path needs to support both, or whether conversion should force a single target encoding.
4. If the DIY/`openslide` fallback path is ever needed for other formats in the same pipeline, confirm the practical impact of OpenSlide's documented NDPI limitations (focal-plane-0-only, `RowsPerStrip`/libtiff workaround) in case any Miqa slides use multi-focal-plane NDPI.
5. Confirm Hamamatsu SDK/license terms via direct outreach (sales/developer relations) — the absence of a public NDP SDK page is not a definitive statement that no such offering exists.
6. Verify version compatibility before adopting: `wsidicomizer`'s PyPI metadata pins `wsidicom>=0.35.0,<0.36.0` and `pydicom>=3.0.0` — check the repo's current/planned `pydicom` version against this floor.
